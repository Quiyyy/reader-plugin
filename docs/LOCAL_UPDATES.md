# Reader 本地更新方案

更新日期：2026-10-29。以下结论基于 Reader 0.2.12 与 Windows Codex 桌面包 26.1023.6621.0（配套 CLI 0.165.0-alpha.1.2）；宿主升级后应重新确认能力。

## 当前采用的流程

本机已验证通过桌面宿主重新安装 Reader，原聊天的页面、后端和注册版本均为 0.2.12，过程中没有重启 Codex。常规交付沿用宿主安装／更新入口，每次仍需单独验收。

1. **准备**：提交候选源码，完成相关检查，只构建、打包和验收同一份包；备份书库、配置和上一版本。
2. **暂存**：调用 `upgrade:windows` 的 `stage` 步骤，登记已验收的本地 marketplace，保留当前运行包，获得明确的安装来源。
3. **宿主安装**：由代理通过 Codex 插件目录的安装／更新入口选择该来源，使原聊天重建 Reader 连接。这一步目前依赖界面操作，无需用户手动点击。
4. **安装核验**：调用 `upgrade:windows` 的 `complete` 步骤，核对注册包、来源提交、文件校验值及持久化数据，更新交付收据。
5. **实际生效核验**：安排一次交付后复核；在原聊天的真实 MCP App 中确认页面与最近后端响应均为目标版本，保存截图及证据，再执行 `reader-host-sync.mjs accept`。新一轮对话或 heartbeat 本身不会替换旧连接。

详细命令与恢复步骤见 [Windows 单包交付](WINDOWS_DELIVERY.md)。真实页面未通过核验时保持 `pending`；独立预览或新服务启动成功不算宿主验收。保留更新期间产生的阅读进度和笔记，不自动用旧书库覆盖新数据。同版本损坏修复可能需要经授权关闭 Reader 进程并重装，不作为普通更新的默认步骤。

## 为什么目前不能只用脚本

外部 CLI 安装会更新文件与注册，但本机实测不能据此确认原聊天连接已替换。官方 `config/mcpServer/reload` 可以请求刷新已加载聊天，前提是调用者连接到**同一个桌面后台**。

本机桌面后台使用 `stdio`，默认控制 socket 不存在。已安装的桌面启动代码在共享 daemon 分支中明确要求 `process.platform !== 'win32'`；因此仅设置 `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1` 不会启用这条 Windows 路径。这是该版本的实现观察，不是永久产品约定。

`--listen unix://` 是 App Server 启动参数，不是已确认可用的桌面 `config.toml` 开关。另起服务再重载，不会刷新原后台。代码中的 WebSocket 地址覆盖入口也不等于为当前进程增加 socket；其桌面兼容性尚未验证。

## 后续可能替代的方案

| 优先级 | 方案 | 采用前提与限制 |
| --- | --- | --- |
| 首选 | 官方宿主安装／更新／重连工具 | 若 Codex 提供可直接调用、作用于原聊天的正式工具，用它替换界面步骤，保留现有验收。 |
| 次选 | 桌面共享后台 + 官方重载接口 | 等待 Windows 桌面正式支持连接同一共享后台；核对进程和原聊天归属，再验证安装、重载及页面刷新。不能只凭 socket 可连接就认定成功。 |
| Reader 自身改造 | 固定连接入口，切换版本化后端 | 需要新增开发，处理进行中的操作、未保存笔记、失败回退和页面缓存；插件清单、工具协议变化仍可能需要宿主更新。当前未实现。 |
| 实验路线 | 桌面连接自管 WebSocket 后台 | 需要改变启动方式，并验证认证、权限、插件和桌面工具；尚无已验证的迁移流程，不作为默认交付方案。 |

每次 Codex 桌面升级或官方工具能力变化时，先复查文档和实际入口，再用隔离书库测试替代流程；通过后在原聊天验收注册版本、来源提交、页面版本、最近后端版本及截图。只有达到现有验收标准，才替换默认流程；不新增周期轮询任务。
