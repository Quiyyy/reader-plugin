# Architecture and safety

## Trust boundary

Book bytes and imported source definitions are untrusted input. Local TXT/EPUB/PDF import accepts only bytes selected by the user or supplied for the specific host file entrypoint; there is no arbitrary local file-path read tool. Local import and reading make no outbound book-resource requests. UI operations remain app-only. All MCP descriptors, including the UI entrypoint, are app-only. UI business results stay in _meta.reader rather than model-facing text or structured output. The internal conversation has a separate dynamic-tool allowlist; no global activation toggles can leak one window's tools into another conversation. Full-book permission is app-only, so a model cannot grant itself access. A dedicated Codex app-server process handles user-requested reading conversations and receives the selected passages/images. There is no analytics or remote font service. Optional Google Drive synchronization adds the separate network boundary described below. The MCP host still transports file/tool payloads, so this is not a claim that host infrastructure cannot process them.

The 0.1.5 online feature has a separate network boundary: explicit source-JSON URL import and enabled-source search/reading use the server-side `OnlineSourceService` and `SafeHttpClient`. This client permits bounded public HTTP(S) requests with validated/pinned DNS, same-origin redirects, TLS checks, cancellation and resource limits. It does not inherit proxies, credentials or cookies, execute source scripts, or read local files. Search terms and online requests go to the user-selected public source; local book bytes are not uploaded. See [the supported subset and limits](online-sources.md).

The stdio server owns storage. Local installation means local storage; deploying this server elsewhere would move that trust boundary and needs separate authorization/security work. The HTTP implementation is a loopback development surface, not a production multi-user service.

## Learning workspace (0.2)

Workspace, NoteEditor and ReadingChat compose the existing TXT/online and structured EPUB readers with a new PDF reader. React UI talks only to the existing ReaderApi adapter: MCP Apps RPC in a host, or the validated loopback API in standalone preview. A floating conversation overlays the document and does not reserve a permanent column. Appearance tokens hold user-selected accent, paper and mode.

The book layout is independent of appearance. study-v1/workspace.json owns folders, notes, annotations, immutable excerpts, book metadata and full-book access choices. Entity revisions reject stale edits; a serialized cross-process store lock and atomic writes persist changes. Undo keeps at most 20 recent edits, bounded to 8 MiB, and verifies the edited entities have not changed. Image assets use SHA-256 names; images and selected excerpts remain independently available after the original book is trashed. This is a bounded single-user store, not a concurrent cloud database: 48 MiB metadata, 2000 notes/folders and 20000 sources/annotations.

Sources use format-specific anchors: original text fragment plus UTF-16 offset, EPUB resource/node/offset, or PDF page/rotation/normalized rectangles. The service validates text against original content before creating a source. A source preview does not overwrite ordinary reading progress. Notebook revisions and user drafts are handled separately so model edits cannot silently replace unsaved typing. Notes export as Markdown, or a ZIP with images and source JSON.

pdf-v1 keeps exact PDF bytes, metadata, page progress and incremental text caches. PDF.js parses in a bounded Node worker; the browser renders with its inline worker handler because the current host CSP disallows blob workers. Font/CMap resources travel through the app-only bridge. No remote assets, active PDF scripts, forms or embedded documents are executed. Passwords and decrypted text for encrypted documents remain in the current service memory; selected excerpts and screenshots are intentionally saved by the user. Scanned documents have no OCR in this version.

study-v1/chats stores messages, drafts, screenshot attachments and optional note binding. Note collaboration exposes only the bound note, its sources and explicitly supplied images; image annotations are normalized vector data in note metadata, and original image bytes remain unchanged. The documented Codex app-server stdio protocol creates independent threads, resumes them for follow-ups, receives streaming deltas and exposes Reader dynamic tools. It is not a desktop chat mirror. Each active turn owns a separate app-server process, which is closed and awaited on completion, cancellation or failure before the topic becomes idle. This releases the persisted thread for another client to resume, archive or delete without interrupting another Reader topic. Follow-ups resume the saved thread through a fresh process; status checks also close their temporary process. Reading conversations default to the bound current book, while independent topics retain selected-source-only access. Cross-book reads are denied regardless of global native-Codex access. The legacy explicit per-turn restriction remains supported by the internal API. Shell, multi-agent, web search, configured external MCP servers and plugins are disabled for these reading threads; unexpected approvals are declined. Stop-before-start races, disconnects and write failures retain visible history. Normal operation uses the official CLI's existing login. An app-only reader_chat_models call pages through model/list and reads the configured default; the temporary discovery process is always closed. A persisted per-topic model is applied to thread/start, thread/resume and turn/start. Reader does not manage tokens. The UI removes folder and note-tag controls while retaining those fields on disk and in updates. A real model test is separate from simulated AppBridge UI acceptance. Run `node scripts/check-reader-codex.mjs --run --ownership` after building to verify cross-client resume, archive and deletion using only its newly created test thread.

Space is an optional native-message content handoff. Reader sends the explicitly chosen note text and images without asking the native model to call hidden Reader tools. Reader remains the note authority; automatic link write-back is not assumed. There is no undocumented Space API, automatic sync or assumed native floating-chat embed.

## Import safety

Compressed-file limit 32 MiB, total declared/actual expanded archive limit 64 MiB, individual entry 16 MiB, up to 2,000 entries, compression ratio up to 200:1. Central-directory/local-header consistency, safe relative paths, unique entry names, supported methods, no ZIP encryption and CRC are checked. Inflation is incremental and output bounded; malformed size declarations cannot simply allocate arbitrary output. EPUB XML custom entities/DTDs are rejected. Encrypted content is rejected; recognized font-obfuscation metadata warns and uses system fallback. Unobfuscated local fonts are supported by the structural EPUB candidate.

The legacy EPUB representation remains original text paragraphs. The structural EPUB candidate reconstructs a closed HTML/attribute/CSS subset in a Shadow DOM, renders sanitized SVG only as images, and requests validated local assets through app-only resource operations. Shadow DOM supplies style isolation; structural reconstruction supplies the security boundary. Book scripts, events, active frames/forms and remote URLs are omitted. TXT/online paragraphs remain escaped React text. See [the production candidate and exact limits](EPUB_CANDIDATE.md). The host UI CSP declares no external connect/resource/frame origins: online fetching happens through app-only MCP calls to the server, not browser fetches to source websites. The loopback preview permits only its own local API through a restrictive HTTP CSP and has no CORS. Negative tests are part of the acceptance suite; this is defense in depth, not a claim of a formal security audit.

## Persistence and locations

Legacy EPUB paragraph traversal is iterative and caches child lists. The rich adapter uses separately bounded depth/node traversal and bounded reconstructed output. Online rules have separate parser, depth, work and output budgets. The preview client aborts ordinary requests after 15 seconds and online operations/book opening after 60 seconds; server-side online work retains its 10-second HTTP and 45-second operation bounds. Failed progress stays available for retry. Dependency overrides pin the UI package's lodash to 4.18.1; use the lockfile and repeat the dependency audit before a later release.

Original bytes are preserved verbatim under their SHA-256 ID. Source-fragment document.json is separate from mutable record.json, so scrolling never rewrites a whole novel. Updates use private file modes, fsync and atomic same-directory rename. Lock directories serialize per-book updates across processes. Settings use their own lock. Saved locators use chapter and paragraph indexes tied to the original-file hash and this normalized representation. They are not EPUB CFIs and cannot silently carry over to a different parser/representation.

Online sources, book records and lazily fetched chapter caches live separately in `online-v1`. Their source revision and stable chapter identifiers preserve online progress/bookmarks without rewriting the local TXT/EPUB representation. Unread online chapters require an enabled reachable source; already cached chapters remain readable when that source is disabled or unavailable.

UI saves are debounced and serialized, stale queued writes are skipped, failed saves are retained and shown with retry, and chapter/book changes flush pending work. Host teardown awaits pending writes when the host supports that lifecycle. Hard kill, network loss, disk failure or a non-graceful close can lose the last unconfirmed position. Two simultaneously active readers follow last successful write; there is no distributed merge of competing reading positions.

## Structured EPUB and further format adapters

The current candidate adds `EpubArchive`, `EpubService`, `EpubDom` and `EpubReader`. Rich state lives in `epub-v2.json`; a resource/node/offset/text location never overwrites legacy paragraph locators. Unique exact migration is required; unresolved data remains available through the old reader. Chapter DTOs/assets load on demand, but bounded archive validation/legacy parsing remains eager. The CSP is unchanged and the adapter creates no nested frames. The pinned Foliate paginator remains a separate diagnostic probe because the current frame policy blocks it; the remaining list below describes future Foliate integration, not the implemented DOM adapter.

The BookDocument boundary separates normalized content from UI and persistence. Rich rendering should be a second representation with versioned locators, never an in-place silent rewrite of saved paragraph locations.

A reviewed candidate is foliate-js MIT commit 78914aef4466eb960965702401634c2cb348e9b1 (observed 2026-10-01). It is intentionally not included as an untested runtime dependency in this release. Upstream states its API is unstable and warns that blob iframe sandboxing alone is insufficient. Before enabling its EPUB/MOBI/KF8 renderer:

1. Vendor/pin the reviewed source and preserve MIT notices
2. Keep archive expansion/DRM validation before renderer import
3. Sanitize book HTML and isolate all book documents from the privileged MCP bridge
4. Add inner-document CSP that blocks scripts, remote content, forms and navigation, including SVG/CSS URL cases
5. Validate host support for nested blob frames without broadening network permissions
6. Save EPUB CFI plus source hash and a text fallback; do not map screen page numbers to durable positions
7. Run malicious EPUB fixtures, WebKit/Chromium tests, real-host tests, plus reflow/resize/resume regression cases

MOBI6, KF8/AZW3, combined MOBI and KFX are different formats. Only DRM-free tested variants may be claimed. Manga follows as a separate image-page representation: CBZ first, natural order, RTL/spreads/vertical strip, bounded image dimensions. CBR and licensed DRM need separate dependencies and review.

## TXT layout version 2

Physical source lines retain their existing chapter/fragment indexes. Optional paragraphStarts groups soft-wrapped Chinese prose for display. Blank lines, new indentation, headings, lists, short verse and speaker transitions prevent merging; uncertain short lines remain separate. Inline fragment anchors retain old reading positions and bookmarks, including multiple bookmarks in one displayed paragraph. Search runs on joined reading paragraphs.

Opening a legacy TXT under the per-book lock re-parses its preserved original with the same encoding, verifies the source hash and exact equality of every chapter fragment array, backs up document/record metadata, then atomically replaces only document layout metadata. The maintenance command `node dist/server/index.js --reflow-text` uses READER_DATA_DIR and performs the same migration without marking books as read. A mismatched source structure is refused, not silently reindexed. Existing processes can continue saving the same locators. No remote upload or public endpoint is part of this migration.

## Prebuilt runtime installation (0.1.3)

The distribution contains all production dependencies rather than relying on a development checkout or attempting to bundle dynamic backend imports. The installer uses only Node built-ins. It validates every packaged file before copying into a versioned stable directory, creates an absolute Node/entrypoint MCP wrapper, and switches a single local marketplace catalog only after a complete version exists. Owned metadata, immutable version directories, a setup lock and retained catalog backups prevent silent overwrites. Interrupted staging and prior versions remain recoverable. User libraries are separate, and setup never creates, migrates or deletes book data. SHA-256 checks detect changed bytes; they are not code signing. Host registration and trust approval remain explicit official-client operations.

## Optional Google Drive synchronization (0.3)

The app-only sync RPCs use a server-side provider restricted to Google OAuth and Drive endpoints. Browser CSP is unchanged. A desktop OAuth client, system-browser PKCE/state and a loopback callback grant only openid/email/drive.appdata. Credentials, vault keys and device identity live in OS credential storage, outside the library; AI tools cannot connect accounts or reveal recovery keys.

The sync engine exports individual entities from existing stores rather than copying workspace.json. Immutable version DAGs use explicit parents, per-device sequences and content digests; local revisions remain local concurrency controls. Remote heads are validated before application. Conditional local writes and a replayable apply journal preserve intervening edits. Captured versions and their baseline are saved together; original local data allows a fresh scan after a crash before capture. Pending preallocated Drive IDs and encrypted upload sessions make ambiguous completion retryable.

AES-256-GCM binds encrypted records/assets to vault and object identity. Assets precede their immutable commit. Changes cursors are discovery optimizations, not ancestry. Missing/changed known history or a missing vault stops synchronization without clearing local content. Conflicting note heads remain available for explicit resolution or copying; foreground dirty drafts survive remote deletion. Per-device positions are selected explicitly rather than taking the furthest page.

sync-v1 contains device-local indices, history, pending files and download caches. A cross-process cycle lock serializes sync without holding the workspace lock over network I/O. Normal local save remains independent of network access; the open UI schedules debounced changes and low-frequency pulls. Unselected preferences, chats, credentials, source configuration, AI grants and caches are excluded. The current immutable history has no garbage collection (128 MiB index / 50,000 versions); deletion is not guaranteed erasure of historical or other-device copies. Local indices remain plaintext, like the rest of the local library.

See [setup, security and limits](GOOGLE_DRIVE_SYNC.md). Protocol/integration tests use two isolated stores; transport tests use fake Google responses, with a real disposable Windows DPAPI test. These do not claim live Google account or macOS/Linux keyring validation.
